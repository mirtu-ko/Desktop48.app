## 0. 前提与边界

| 项                | 事实                                                                                                                                             |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 应用形态          | Electron 桌面应用，主窗口与独立播放窗均为 `frame: false` 无边框窗口                                                                              |
| 视口单位          | 无边框下 `window.innerWidth/innerHeight` 即窗口内容区 CSS 像素；`100vw/100vh` 与之同源                                                           |
| DPI 处理          | 未调用 `webFrame.setZoomFactor` / `deviceScaleFactor`；工作区来自 Electron `screen.getPrimaryDisplay().workArea`（DIP），由 OS/Electron 处理 DPI |
| 页面缩放          | 应用不管理 Ctrl+/- 页面缩放；`Lives.vue` 注释明确宽度断点「正常窗口不会触发（minWidth 900），仅在页面缩放时」生效                                |
| 唯一显式 DPR 逻辑 | `MemberBirthdayCard.vue:274` 撒花画布，`ratio = Math.min(window.devicePixelRatio \|\| 1, 2)`，再 `setTransform` 放大绘制坐标                     |
| 无障碍降级        | 多处 `prefers-reduced-motion: reduce` 关闭动画（与分辨率无关，但同属「环境信号 → 样式」体系）                                                    |

**结论**：这不是 Web 响应式站点，而是「窗口几何（主进程） + 视口连续插值（CSS） + 少量离散断点」三层协同的桌面适配体系。

## 1. 主窗口初始几何：`src/main/window-bounds.ts`

### 机制

```
fitEdge(area, preferred, min):
  wanted = max(preferred, round(area * WIDE_SCREEN_RATIO))
  withGap = area - 2 * WINDOW_EDGE_GAP
  return min(wanted, min(area, max(withGap, min)))
```

宽、高各自独立套用该公式，然后：

```
aspectCap = max(minWidth, round(height * WINDOW_MAX_ASPECT))
width = height < preferred.height ? min(rawWidth, aspectCap) : rawWidth
```

关键常量：`WINDOW_PREFERRED = 1400×900`、下限 `720×560`、`WIDE_SCREEN_RATIO = 0.65`、`WINDOW_EDGE_GAP = 32`、`WINDOW_MAX_ASPECT = 1.7`。

- 下限随实际尺寸一起收敛（`computeWindowBounds` 返回的 `minWidth/minHeight` 被夹到初始尺寸以下），避免 Electron 把窗口强行抻出屏幕。
- `centerWindow()` 显式传 `x/y`；副屏坐标按 workArea 原点偏移，不会被归零。
- `display-metrics-changed` 触发 `refitMainWindowToDisplay()` → `fitWindowToWorkArea()`：只在越界时推回新工作区，**不放大、不重新居中、跳过最小化/最大化/全屏**，因此不覆盖用户手动调过的尺寸。

### 实测档位（来自 `test/window-bounds.test.ts`）

| 工作区                   | 初始窗口         | 说明                                        |
| ------------------------ | ---------------- | ------------------------------------------- |
| 1280×705                 | 1090×641（x=95） | 高度压到 641，宽度被 1.7 夹到 1090          |
| 1366×728                 | 1129×664         | 四边各让 32，再按 1.7 收窄                  |
| 1440×805                 | 1260×741         | 同上                                        |
| 1536×832（1080p@125%）   | 1306×768         | 768 刻意留在常规档                          |
| 1920×1040                | 1400×900         | 与旧版逐像素一致                            |
| 2560×1346                | 1664×900         | 宽屏按 0.65 放大，宽高比 1.85 不受 1.7 约束 |
| 3840×2055（4K@100%）     | 2496×1336        | 宽高同时放大                                |
| 853×533（1280×800@150%） | 789×533          | 工作区小于下限时放弃留白                    |
| 640×480                  | 640×480          | 下限让位于「绝不超屏」                      |

### 我看法

**优点**：把「屏幕尺寸 → 窗口尺寸」收敛成一个纯函数，且测试用真实断言钉住每一档；显式 x/y 处理了 Windows 层叠与副屏原点；显示器变化只做越界收敛而非重排，尊重用户控制权。这些都是踩过坑之后的正确抽象。

**隐患 1 — 注释与代码不一致**：`window-bounds.ts:33` 注释写「阈值是工作区宽 1944」，但公式给出 `1400 / 0.65 = 2154`，`test/window-bounds.test.ts:69` 也明确写「阈值 2154」。**以 2154 为准**，注释疑似早期比例残留。外部 AI 请以公式/测试为准。

**隐患 2 — 0.65 的放大是产品决策而非技术必需**：4K 下窗口达到 2496×1336（占工作区 65%），这会让所有依赖 `vw/vh` 的连续量同时跑到曲线高端，卡片变成 10/7/8 列（见 §4），与「1400 满意档」的观感差异很大。若高级 AI 评估「一致性」，这是最值得追问的一点：**窗口是否应该随屏幕放大到这个程度，还是应该锁在 1400 并依赖系统缩放？**

**隐患 3 — 1.7 约束的不对称**：只在高度被压低时生效，所以同为 900 高，1920 屏是 1400×900（1.56），2560 屏是 1664×900（1.85）。这是刻意保留宽屏放大，但意味着「同一应用在不同屏上形状不同」无法完全消除。

## 2. 独立播放窗几何：`src/common/float-window.ts` + `src/main/float-window.ts`

### 机制

与主页**完全不同的一套尺寸策略**：按视频宽高比内接，而不是按固定基准窗口收敛。

- 建窗兜底宽高比 `FLOAT_DEFAULT_ASPECT = 9/16`；真实元数据到达后调用 `fitFloatWindowAspect()` 整体重算。
- 工作区锚点：`1280×800` 与 `1920×1080`，在两者之间线性插值比例：
  - 横屏视频区宽度占工作区宽：`0.53 → 0.45`
  - 竖屏视频区高度占工作区高：`0.80 → 0.70`
  - 锚点区间外固定取端点比例。
- `fitAspectInBox(aspect, boxW, boxH)`：宽度优先内接，超高则按高回缩，四舍五入到整像素。
- 视频区最小宽：竖屏 320 / 横屏 680；`FLOAT_EDGE_MARGIN = 24`；标题栏 `FLOAT_BAR_HEIGHT = 36` 计入窗口高；窗口硬下限 240×160。
- 比例定形状态机 `decideAutoFit()`：`autoFitSettled=false` 时无条件定形并清零 `userResized`（Windows DPI 取整、Linux `will-resize` 不触发都会误报）；落定后尊重用户缩放，Linux 用「当前尺寸偏离上次程序设置值超过 epsilon」兜底反推。
- 定形时保持右上角不动、整体重算并夹回工作区；位置为右上角锚点 + 对角级联 28px，步数用尽回绕。
- 电台窗（`liveType === 2`）固定 `360×640`，**不随分辨率自适应**，只受最小尺寸约束。

### 我看法

**优点**：比例内接 + 连续插值是正确解法——它避免了「直接套大屏比例导致 1440 屏窗口反而比 1280 屏小」的非单调结果（注释里明确记录了这个坑）；状态机把「系统取整」与「用户接管」分开，是跨平台窗口管理的成熟做法；主进程/渲染端共用同一份纯函数常量，避免两侧漂移。

**隐患 1 — 电台窗未做工作区收敛**：`computeInitialWindowSize()` 会把结果夹回工作区，但电台走 `FLOAT_RADIO_WINDOW_SIZE` 分支直接建窗，固定 360×640 没有同样的夹取。极小工作区（如 640×480）下可能超出；`resolveFloatWindowPosition()` 只夹 x/y 不夹尺寸。建议把它也接到同一收敛函数（aspect 无意义时传某个固定比例即可）。

**隐患 2 — 字面量字符串跨层契约**：弹幕避让量是 JS 里的 CSS 字符串 `calc(var(--fp-capsule-btn) + 2 * var(--fp-capsule-pad) + var(--fp-control-gap))`（见 §6），改 token 名不会有编译期报错，只能靠测试文本断言兜底。

## 3. 高度轴：从离散档位演进为连续插值

### 机制

这是当前代码与旧设计**差异最大**的部分，外部 AI 请勿按「两级密度档」理解。

**信号层**（仍保留）：

- `src/common/density.ts`：`DENSITY_BREAKPOINT = 760`，`resolveDensity(h) = h <= 760 ? 'compact' : 'regular'`
- `src/renderer/src/utils/apply-density.ts`：唯一写入口，同值不写；`installDensitySignal()` 首帧同步写入，之后只在 `matchMedia('(max-height: 760px)')` 跨越断点时重算
- `src/renderer/src/main.ts:21`：`installDensitySignal()` 在 `app.mount` 之前调用，主窗口与播放窗都装

**连续层**（主力）：

- `src/renderer/src/assets/css/_fluid.scss` 的 Sass 函数 `fluid($min, $max)` → `clamp(min, min + Δ * var(--vh-step), max)`；负数差值自动交换 clamp 两端（用于负外边距）
- `--vh-step: calc((100vh - 641px) / 259)` → 641px 高为 0，900px 高为 1，两端由 clamp 封顶
- 9 个 `.vue` + `app.scss` 各自 `@use '.../fluid' as *` 引入，约 70 处调用

**全局高度 token（两端值 = 原紧凑档/基准档）**：

| token                 | 641px   | 900px      |
| --------------------- | ------- | ---------- |
| `--radius-card`       | 16px    | 20px       |
| `--tabbar-offset-top` | 50px    | 64px       |
| `--float-top`         | 8px     | 12px       |
| `--dock-reserve`      | 80px    | 96px       |
| `--card-body-pad`     | 7/9/9px | 10/12/12px |
| `--dock-item-w`       | 46px    | 56px       |
| `--dock-icon`         | 32px    | 40px       |
| `--dock-gap`          | 5px     | 8px        |

**离散层只剩「不能连续变」的结构规则**：`:root[data-density='compact']` 在 `app.scss:154-180` 仅覆盖 4 类：EP 普通按钮 32→28px、两处字号台阶（`.section-title`、`.detail-side-title`）、详情弹窗高度上限 86vh→90vh（分别封顶 660/640px）。

### 测试守卫（`test/density-breakpoint.test.ts`）

- 全仓禁止任何 `@media (max-height:…)`；紧凑样式标记只允许出现在 `app.scss` 一处
- `compactOverrides()` 必须为空数组（紧凑档不再覆盖任何自定义属性）
- `--vh-step` 两端锁定 641/900；8 组全局 token 的声明必须**只由 fluid() 组成**，多一个硬编码值就失败
- `fluid()` 只有一份实现，两端不得相等（相等即死曲线，且不会报错）
- `installDensitySignal()` 必须在 `app.mount` 之前

### 我看法

**优点**：这是本项目最值得称道的设计演进。把「窗口矮 1px 整页跳一格」的离散跳变换成连续曲线，同时保留一个离散信号只负责真正无法插值的结构量（构建期固定的 EP 按钮高度、字号台阶、弹窗高度语义），**职责切分干净**。测试直接解析源码而不复制常量，能拦住「曲线被悄悄写死」这种肉眼极难发现的回归，属于高价值守卫。

**隐患 1 — 双轨交界仍有一处跳变**：h=760/761 时，连续量走曲线（此时 `--vh-step ≈ 0.46`，处于中间态），但按钮高度、两处字号、弹窗高度会瞬间切换。这不是 bug，但外部 AI 若评估「无缝性」，应指出这是**唯一残留的离散边界**，且它与曲线中段重叠，视觉上可能比纯离散档更突兀。可考虑把这些结构量也改由 JS 注入变量（而非 CSS 属性覆盖）。

**隐患 2 — 曲线锚点固定 641/900**：窗口可低于 641（下限 560）也可高于 900（4K 下 1336），两端之外的量被 clamp 冻结。小窗继续变矮时留白不再收缩，大窗继续变高时留白不再增长。这是有意取舍，但意味着「4K 大窗」的疏密感与 900 高完全一致，配合 §1 的放大策略会放大观感差异。

**隐患 3 — 字号台阶没有连续化**：除两处例外字号，正文保持固定 px。大窗上文字相对变小、小窗上相对变大；若目标是「视觉密度一致」而非「物理尺寸一致」，这是缺口。

## 4. 宽度轴：vw + clamp + auto-fill 网格

### 机制

**水平内距**：`--space-page-x: clamp(12px, 1vw, 32px)`，全项目**只有一个定义**，紧凑档不覆盖。下限 12 保住 1280 屏 5 列，系数 1vw 留约 2.68px 余量（记忆中记录：1.1vw 只剩 0.25px，故不可随意调）。

**网格间距**：`--card-gap: clamp(12px, 1.15vw, 16px)`、`--show-gap: clamp(15px, 1.43vw, 20px)`，系数 = 基准值/1400，≥1400 逐像素回到旧常量。

**卡片最小宽**（`min()/max()` 组合）：

```
--card-min  = min(clamp(200px, 16.1vw, 225px), calc((100% - 3 * var(--card-gap)) / 4))
--show-min  = min(300px, max(clamp(230px, 18.6vw, 260px), calc((100% - 3 * var(--show-gap)) / 4)))
--album-min = min(265px, max(clamp(215px, 17.2vw, 240px), calc((100% - 3 * var(--card-gap)) / 4)))
```

- `calc((100% - 3*gap)/4)` 让窄窗保持至少 4 列等比收窄，而不是掉列后单卡撑大（直播带 200–265、公演 230–380、专辑 215–335）。
- 基准 225 由「1216 窗口排 5 列」与「1920 窗口仍排 7 列」的唯一交集锁定，区间仅约 1.6px——这是极窄的容错窗口，属于关键不变量。
- 专辑卡内部尺寸同源收窄：`--album-cover` 86→96、`--album-vinyl` 74→82、`--album-label` 30→34、`--album-inner-gap` 20→32、`--album-inset` 9→12，卡高由基准 120 降到约 104–105（`cover + 2 * inset`，取决于窗口宽落在插值段的哪一点）；`Albums.vue` 的黑胶位置、盘标负边距、骨架屏尺寸都引用这些变量。

### 实测列数 / 单卡宽（测试求值，常规与紧凑两档逐像素一致）

| 窗口宽 | 直播       | 公演      | 专辑                  |
| ------ | ---------- | --------- | --------------------- |
| 1090   | 5 / 203.2  | 4 / 254.8 | 4 / 257.1             |
| 1260   | 5 / 235.4  | 4 / 295.2 | 4 / 297.8             |
| 1400   | 5 / 261.6  | 4 / 328   | 4 / 331（用户满意档） |
| 1920   | 7 / 255.1  | 5 / 360.3 | 6 / 300.3             |
| 2496   | 10 / 230.2 | 7 / 332.3 | 8 / 291.8             |

### 测试守卫

`test/density-breakpoint.test.ts` 自带一个受限 CSS 表达式求值器（`min/max/clamp/calc/var/px/vw/%`），**从源码读变量而非复制数值**，断言：

- ≥1400 与改动前固定常量逐像素一致（列数与卡宽）
- 同宽换高度档，列数与卡宽必须相等
- 1.7 收窄后的新宽度列数不少于原宽度
- 窄窗下公演/专辑单卡不低于地板 230/215
- 遇到未登记的 `calc` 写法直接抛错，避免静默算错

### 我看法

**优点**：「宽度决定列宽、高度决定留白」的正交分解非常干净，直接解决了「同宽换窗高就换列数」这类难查 bug；`clamp(下限, 基准/1400 * vw, 基准)` 的系数设计让 ≥1400 完全无回归、<1400 连续收一档，兼顾了兼容性与小屏可读性；`/4` 项保证窄窗掉列时的体感连续。

**隐患 1 — 测试求值器是浏览器语义的近似**：`Math.floor((content + gap) / (min + gap))` 是 auto-fill 的理想模型，但浏览器对 `min()` 混合 `%`/`vw`、亚像素取整、`auto-fill` 与 `auto-fit` 的差异可能与模型不同。项目约定本来就是「真布局用无头 Chrome + 最新构建产物复刻」，这些信息未进入 CI。**建议外部 AI 把「需要真实浏览器回归」列为该策略的主要验证缺口。**

**隐患 2 — 225 的容错区间只有 1.6px**：任何调整 `--card-gap` 系数或 `--space-page-x` 的改动都可能同时破坏「1216 排 5 列」和「1920 排 7 列」。测试能拦住，但调参空间极小，属于脆弱点而非稳健点。

**隐患 3 — 窄窗断点与连续轴的关系**：宽度主要是连续的，但 §5 的 5 个离散断点会在特定宽度突然隐藏整块 UI（房间右栏、设置左导航）。连续与离散混用的边界需要外部 AI 评估是否可接受。

## 6. 独立播放窗浮层尺寸轴：`.fw-root`

### 机制

`app.scss:1463-1479`，挂在 `.fw-root`（FloatWindowApp）而非 `:root`，主窗口取不到也不会串味：

```
--fp-step: calc((100vw - 320px) / 580)   // 320 → 900 线性推进，两端 clamp
```

| token              | 320px 端 | 900px 端 |
| ------------------ | -------- | -------- |
| `--fp-btn`         | 28px     | 40px     |
| `--fp-capsule-btn` | 25px     | 34px     |
| `--fp-capsule-pad` | 2.5px    | 5px      |
| `--fp-icon`        | 14px     | 20px     |
| `--fp-font`        | 11px     | 13.5px   |
| `--fp-font-sm`     | 10px     | 12.5px   |
| `--fp-gap`         | 3px      | 7px      |
| `--fp-control-gap` | 8px      | 12px     |

- 下端对应竖屏小窗（9:16 常见 320–430 宽），整体比早期固定值收紧约 12%；上端即原固定值，所以大窗逐像素不变。
- `MediaIcon` 一律**不传 `:size`**：其 size 是内联 style 会压过 CSS，省略时是 `1em`，由按钮 `font-size` 决定边长。
- 弹幕布局（`use-danmaku-layer.ts`）：
  - 字号 = `clamp(min, max, round(shortSide * 0.033))`；`shortSide = min(rect.width, rect.height)`
  - 上限分三态：紧凑 `[10,14]`、窗口态 `[12,14]`、全屏 `[12,18]`（非全屏小窗若沿用 18 会显得拥挤）
  - 横向锚视频渲染区（左右/顶内缩 10px），纵向贴**窗口**；左侧浮栏仅当黑边 ≥60px 才可用
  - 底边避让 `DANMAKU_CONTROL_CLEARANCE = calc(var(--fp-capsule-btn) + 2 * var(--fp-capsule-pad) + var(--fp-control-gap))`——把胶囊高度与悬空量写成一条算式，改钮径不必手算

### 测试守卫

`density-breakpoint.test.ts` 断言步长锚在 320/900、8 个 token 全部形如 `clamp(low, calc(low + k * var(--fp-step)), high)`、起点等于下限、两端不等（死曲线不会报错，只能靠断言拦）。`test/danmaku-layout.test.ts` 与 `test/danmaku-overlay.test.ts` 覆盖字号/几何计算。

### 我看法

**优点**：这是「按容器宽度线性插值浮层尺寸」的教科书式实现，锚点选择贴合真实场景（竖屏 320–430、横屏 640–900）；把弹幕避让量写成 token 算式而不是硬编码 46px，消除了改按钮尺寸后忘记改避让量的经典隐患；跨文件共用的量才提 token，单点间距仍写 inline clamp，避免过度抽象。

**隐患**：这条轴的输入是 `100vw`，即**窗口内容宽**，而弹幕字号输入是**视频渲染区短边**——两者在 letterbox 黑边很大时会明显不同步（窗口很宽但画面很窄时，控制条很大、弹幕很小）。这是有意的（注释说「短边与画面宽度同阶，横竖屏下气泡占画面比例才均匀」），但外部 AI 若评估「视觉协调性」，这是值得讨论的取舍。

## 7. 其他分辨率相关细节

- **应用图标**：Windows 用与安装包 exe 同一份多尺寸 ico（16~256 各档），macOS/Linux 用带留白方形图稿；`app.ts:131-135` 注释指出直接用 macOS 图稿会让 Windows 任务栏图标缩小约 19%。
- **高 DPI 画布**：生日撒花 canvas 按 `min(DPR, 2)` 扩像素并 `setTransform`，兼顾清晰度与性能上限。
- **更新弹窗/详情卡高度**：基准 `min(86vh, 640px)`，紧凑档放宽到 `min(90vh, 660px)`（履历卡仍 640）。
- **无 CSP 启用**：媒体/脚本域动态且有回归史，与分辨率无直接关系，但意味着样式/资源来源不受策略约束。

## 9. 我的总体判断（供高级 AI 重点审阅）

### 做得对的地方

1. **分层清晰**：主进程窗口几何 / 播放窗几何 / 高度连续轴 / 宽度连续轴 / 少量离散断点 / 浮层独立轴，各管各的，且有明确的「不改写对方变量」纪律。
2. **单入口纪律**：密度写入口、fluid 实现、窗口几何函数、浮层 token、断点登记表都是单点；新增量必须先找到归属层。
3. **向后兼容被形式化**：「≥1400 逐像素不变」不是口头承诺，而是用改动前常量做逐项断言。
4. **对「静默失效」有专门守卫**：死曲线、重复定义、残留媒体查询、未登记断点，都会让功能「看起来正常但策略已失效」，测试专门拦这类问题。
5. **尊重用户控制**：显示器变化只收敛不重排；播放窗用户手动缩放后停止自动定形。

### 需要高级 AI 重点评估的问题

1. **窗口随屏幕放大到 65% 是否合适？** 4K 下 2496×1336 会让布局跑到所有曲线的高端（10/7/8 列），与「1400 满意档」观感差异大。这是全局一致性问题的最高优先级。
2. **离散密度信号是否仍有存在必要？** 连续轴已接管绝大部分垂直量，只剩 4 类结构规则在 h=760 跳变；能否把这些也变量化，从而彻底去掉 `data-density`？
3. **连续轴的插值模型缺少真实浏览器验证**：CSS 求值器是简化模型，未覆盖亚像素/容器查询/Element Plus 内部；是否应引入无头 Chrome 布局回归到 CI？
4. **`--vh-step` 用 `100vh`**：在 Electron 无边框窗口下成立，但若用户页面缩放或未来引入自定义标题栏高度，`100vh` 与 `window.innerHeight` 的等价性可能被打破，需要重新审视。
5. **字号未随窗口连续缩放**：大窗上文字相对偏小，若目标是「视觉密度一致」而非「物理像素一致」，需要引入根字号/字号曲线；若目标是后者，则现状合理，需明确写进设计原则。
6. **电台播放窗固定尺寸未夹回工作区**、**弹幕避让的跨层字符串契约**，是两个具体的技术债点。
7. **注释陈旧**：`window-bounds.ts:33` 的「1944」应为「2154」（公式与测试双重确认）。建议修正，避免误导后续维护者与 AI 分析。
8. **脆弱不变量**：`--card-min` 基准 225 的可用区间仅约 1.6px，依赖测试守住；任何间距/内距调整前都应先跑 `density-breakpoint` 测试。
